# WTree — Design Document (v0)

A keyboard-driven file manager for the terminal, in the spirit of XTree Gold, ytree, and Midnight Commander. Cross-platform from day one. Optimized for fast tree navigation, persistent tagging across directories, and clean composition with external tools.

## Status

This is a **living design document**. Open questions are marked `OPEN` and need to be resolved before implementation begins; confirmed decisions are stated declaratively. Update as the design evolves.

## Lineage

WTree borrows from three traditions:

- **XTree / XTree Gold / ytree** — single hierarchy view, persistent tagged set across directories, the "logged" disk metaphor.
- **Norton / Midnight Commander / Far** — dual-pane TUI layout, function-key conventions, modal dialogs.
- **Modern Unix (ranger, nnn, lf, yazi)** — composition with external tools, sane defaults, lazy I/O.

The goal: XTree's feel and tagging power, MC's visual layout, and a modern Unix selection-as-output escape hatch underneath.

## Core architecture

### EntrySource abstraction

The disk is read through a pluggable `EntrySource` interface. Anything that can yield directory entries for a path qualifies. Implementations in v0:

- **NativeSource** — direct OS calls (`readdir`, `FindFirstFile`, `std::fs::read_dir`, equivalent).
- **ShellSource** — shells out to `dir /b /s /a` on Windows or `find … -printf` on Unix and parses output. Used as a fallback when native readdir is unreliable (bad sectors, weird drivers, frozen network mounts).
- **MockSource** — scripted contents and scripted errors, for tests.

Future (post-v0): **ArchiveSource** (`.zip`, `.tar`, `.tar.gz` as virtual directories), **RemoteSource** (SSH/SFTP). The interface shape is designed to admit these without core changes.

The rest of WTree never knows what kind of source it is looking at.

### Entry shape

Each entry contains at minimum: name, kind (file/dir/symlink/other), size, mtime. Optional fields (permissions, owner, link target) are nullable. A source advertises its *capability* — what fields it can supply — so the UI can render "permissions unknown" gracefully when a source can't provide them.

Dates are stored canonically as **`YYYY-MM-DD HH:MM:SS`** (ISO 8601 with seconds resolution). All sources convert their native date formats into this on the way in; nothing locale-flavored is ever passed to the UI. Display formatting (e.g. relative — "2h ago") is a presentation-layer config knob, applied only at render time.

### Errors as data

A scan yields `Result<Entry, ScanError>` per item. Permission-denied or I/O failure on one subdirectory does **not** abort the scan — the broken node appears in the tree as a damaged entry (visually distinct, navigable past). This is the correct behavior on healthy disks too; it's also what makes the unreliable-disk story work end-to-end.

### Traversal strategy

The `EntrySource` interface is **lazy per directory**: you ask for a path, you get its immediate children. "Log the whole tree" semantics live one layer up as composable strategies:

- **LogAll** — eager full-tree scan (XTree mode). Best for SSDs and small trees.
- **LogOnDemand** — scan as the user navigates. Default.
- **LogDepth(n)** — eager scan to depth `n`, lazy below.
- **LogPersist** — scan once, persist to disk, restore on next launch.

An unreliable-disk source can refuse `LogAll` if it knows the device is fragile.

### Tagged set

The tagged set is the central object — files tagged anywhere in the tree persist as the user navigates. Single keystroke to tag/untag. Operations (copy, move, delete, etc.) apply to the tagged set when one exists; otherwise to the entry under the cursor.

This is what makes XTree's model powerful and what differentiates WTree from a plain dual-pane file manager.

## User interface

### Layout

**Decided: Explorer-style coupled panes.** Left pane is a navigable folder tree; right pane shows the contents of whichever folder is selected in the tree. The panes are coupled — two views of one selection. The MC source-and-destination ergonomic is replaced by the tagged set (below), which makes cross-directory operations first-class regardless of where the panes are pointing.

### Tagged set scope

The tagged set is **per-session, source-agnostic.** A tag is a `(source_id, absolute_path)` tuple, not a bare path. The set can simultaneously hold entries from:

- different drive letters on Windows (`C:\foo`, `D:\bar`)
- UNC / network paths (`\\server\share\baz`) — these work for free via NativeSource on Windows because Win32 handles UNC transparently
- different mount points on Unix
- post-v0 sources (archive contents, remote/SFTP) once those land

**Operation semantics vary by source pairing.** Cross-drive move is copy-then-delete, not rename. Cross-source operations (e.g. copy from a future SFTP source to local) need explicit transfer logic. Every operation asks the relevant sources "can you do X" before promising the user it will happen instantly; the UI shows a progress dialog for non-trivial transfers.

**Enumeration of network shares** (browsing what exists on a network, as opposed to typing `\\server\share` directly) is parking-lot material — see below. v0 supports UNC paths you can address; it does not browse for servers or shares.

### Editing files

Shell out to the user's editor. Resolution order:

1. `$VISUAL`
2. `$EDITOR`
3. Platform default — `notepad` on Windows, `nano` then `vi` on Unix-like.

An inline editor is **explicitly out of scope for v0** — see Parking lot.

### Modular yield mode

A flag (working name `--pick`) makes WTree behave as a selector: launch, navigate, tag, press a confirm key, WTree prints the tagged set to stdout and exits with status 0 (or non-zero if cancelled). This lets it compose with shell pipelines and external scripts:

```
wtree --pick | xargs cp -t /backup
```

Common operations (copy, cut, paste, move, delete, rename) remain single-key and internal for the snappy keystroke feel. `--pick` is the escape hatch for everything else.

### Keymap

**Decided: XTree single-letter commands as primary, MC function keys as aliases.** Same operation, two bindings. Vim modal explicitly rejected. Alt-modifier accelerators added as an optional layer for Windows-style menu navigation; Alt is never required for any action.

#### Modality

Pane focus determines arrow-key behavior. In the tree pane, ← collapses / → expands the node under cursor — with one exception: **← on the root node ascends**, re-rooting the tree at the parent directory ("log the directory above"). At the filesystem root the action no-ops with a status-line nudge. In the contents pane, ← goes to parent dir / → enters the highlighted dir.

Modal dialogs (typing a destination path, typing into a search prompt) re-bind letter keys to text input. Same principle as `/` putting you in incremental-search mode: while a dialog or search is active, letters are text, not commands. The status line shows the active mode.

**Incremental search (`/`)** is modeless inline, not modal. Pressing `/` swaps the StatusLine row for a SearchBar in the same slot. While the SearchBar holds focus: printable characters extend the query and the focused pane's cursor jumps to the first match (substring, case-insensitive) at or after the original cursor position; Backspace shrinks the query; Down or `Ctrl+G` step to the next match (wrap); Up steps to the previous match. Enter commits — the cursor stays at the current match, search exits. Esc cancels — the cursor restores to the pre-search position, search exits. Empty query is a no-op (cursor doesn't move). No-match is indicated visually (the bar text turns red, shows `(no match)`). Search is local to whichever pane had focus at `/`-press time; the other pane is unaffected.

#### Selection rule

Commands operate on the tagged set if it is non-empty; otherwise on the entry under the cursor. **Rename is the exception**: it is a single-entry operation in v0. If `R` is pressed while the tagged set is non-empty, the operation is rejected with a status-line nudge ("rename works on one entry; clear tags first"). Batch rename is parking-lot material for post-v0.

**Make-new is also exceptional**: it doesn't consume the tagged set or the cursor entry. The parent directory is `ContentsPane.current_path` — whatever the user is *looking at*. Tagged set is silently ignored (mirrors View / Edit). The sub-prompt is two screens: a kind chooser (D/F/Esc) then a name PromptDialog; the typed name may contain forward-slash separators, in which case intermediate directories are created on apply (lenient mode).

#### Cross-platform modifier strategy

The choice of which modifier keys WTree binds is constrained by what TUI applications actually *receive* on each platform. Three layers diverge here — physical key, OS keycode, and what the terminal forwards to the app — and the design honors the terminal layer.

**Win / Super / Cmd is never bound.** This key occupies the same physical position across PC and Mac keyboards but does not reach terminal applications on any major platform. Windows reserves it for the shell (`Win+E`, `Win+R`); macOS routes `Cmd+anything` to the active app's menu bar before the terminal sees it; Linux window managers typically grab Super for tiling and workspace operations. A design that depends on this key is dead on arrival in a terminal.

**Ctrl is the bedrock.** Reliable across every terminal on every platform; used for system-level and meta operations (`Ctrl+A` tag-all, `Ctrl+U` untag-all, `Ctrl+R` refresh, `Ctrl+F` find-across-tree, `Ctrl+G` next match, `Ctrl+I` properties).

**Alt is an optional accelerator layer, never a requirement.** It reaches the terminal as `meta+letter` (Textual's term) on Windows and Linux without configuration. macOS users must enable "Use Option as Meta key" in their terminal preferences (iTerm2: Profiles → Keys; Terminal.app: Profiles → Keyboard) — this is called out in the README. AltGr on European keyboards is a typed-character key, not a modifier; never use right-Alt-only bindings.

Every Alt-based action has at least one non-Alt path: F9 opens the menu bar (MC convention) and arrow keys navigate it; single-letter and F-key commands cover every primary operation. A user who never presses Alt loses nothing.

### Progress dialog

For copies, moves, and deletes that exceed a size or duration threshold, a centered `ModalScreen` reports live progress. Below the threshold the existing StatusLine `Copy N/M` indicator carries on alone — flashing a modal for three text files is worse than no feedback.

**Delayed-show threshold.** Show only if any of:

- `bytes_total > 4 MiB`, OR
- `items_total > 50`, OR
- the operation has been running for `400 ms` and is not yet finished.

Operations resolving to instant kernel calls (same-drive `os.rename`-style moves, deletes of empty dirs) never trip the threshold and never show.

**Layout.**

```
┌─ Copy ─────────────────────────────────────────────┐
│ photos/IMG_4521.JPG                                │
│   → /backup/photos/                                │
│                                                    │
│ [████████████▌░░░░░░░░░░░░░░░] 47%                 │
│                                                    │
│ Elapsed  00:14    Data     214.3 MB                │
│ Rate     15.3 MB/s    Drag    7.42                 │
│ Files    3 / 12                                    │
│                                                    │
│                Esc = Cancel                        │
└────────────────────────────────────────────────────┘
```

**Readouts.**

- **Percent** — byte-percent of the whole plan, `bytes_done / bytes_total`. The bar is byte-weighted, not item-weighted; a 10 GB file followed by 50 small ones won't sit at "1 of 51" until the big one finishes.
- **Elapsed** — `now − started_at`, `MM:SS` (or `H:MM:SS` past one hour).
- **Data** — `bytes_done`, scaled to `KB` / `MB` / `GB` to one decimal.
- **Rate** — `bytes_done / elapsed_seconds`, scaled. Renders `—` when the op produced zero bytes (instant rename-moves) — see the zero-time guard below.
- **Drag** — `(1 − bytes_done/bytes_total) × elapsed_seconds`, normalized to fraction-seconds. A "patience tax" — rises as you wait, peaks mid-op, returns to zero at completion. *Not* a buffer or queue depth; a derived vibe number. The label stays `Drag` on screen regardless of how the value reads on a given run.
- **Files** — `items_done / items_total`. Preserves the existing N/M signal for sanity-checking against Percent on heterogeneous plans.

**Zero guard.** Any readout whose formula touches `elapsed_seconds` *or* `bytes_done` skips the math entirely while either is zero and renders `—`. The two cases this catches:

- `elapsed_seconds == 0` — divide-by-zero on Rate, all-zero opening-paint on Drag, wildly-lying Rate that a single sub-second chunk would produce.
- `bytes_done == 0` (with elapsed already ticking) — happens when a big file has been opened but the first read hasn't returned yet. Rate would read a flat `0.0 MB/s` and Drag would spike to its theoretical maximum at second one, both implying meaningful information when nothing has actually moved.

Once both sides are non-zero the readouts go live and stay live for the rest of the operation.

**Cancellation.** `Esc` requests cancel; the dialog header switches to `Cancelling…` and the active item finishes (partial files are not left half-written — the chunk callback returns `False` to break the copy loop, and any partial file is cleaned up). Already-completed items stay done. Plan-complete posts the usual `_on_plan_complete`, which fires `notify()` since the user may have looked away.

**Mid-plan cancellation.** Cancel doesn't just stop the in-flight item — it also stops the rest of the plan. `apply_plan` takes an optional `is_cancelled: Callable[[], bool]` and checks it at the top of the per-item loop. The queue passes a closure that reads its own `_cancel_requested` flag. Once the flag flips, every remaining `PlanItem` short-circuits to `ItemStatus.SKIPPED` with message `"cancelled"`; the per-item `progress` callback still fires for each so the dialog's items counter stays consistent and the existing partial-state accounting (bytes_done credits only `SUCCESS` items) keeps working unchanged.

The status split is deliberate. The in-flight item that gets cancelled mid-copy stays `FAILED("cancelled")` — we ran it, it didn't complete, partial bytes were thrown away. Items we never started are `SKIPPED("cancelled")` — distinct semantic, and `OperationResult.summary()` already breaks out `N ok M skipped K failed` so the user sees the difference without any UI changes. A future unified `ItemStatus.CANCELLED` is on the table for a later refactor; not worth the enum churn this pass.

Pre-item, not mid-item. The check runs *before* each call to `_apply_item`, so the boundary is clean: once cancel fires, no new items start. Mid-item cancellation (the chunk-callback returns False path) is already wired and remains the only way to stop work inside an item. A 50-file plan cancelled at item 5 sees: 4 SUCCESS, 1 FAILED (cancelled mid-copy), 45 SKIPPED (never started).

**Minimize / resume.** A long copy shouldn't trap the user. `m` (lowercase) on the dialog **minimizes** — dismisses the modal without setting `cancel_requested`; the queue keeps copying in the background. `Ctrl+P` (global) **resumes** — re-pushes a fresh `ProgressScreen` bound to the same `OperationQueue`, which polls the live state and re-derives every readout the instant it paints. No state is duplicated: the queue is the single source of truth and the dialog is a pure view over it (this is also why the new screen comes up at whatever percentage the op has actually reached, not a stale snapshot from when the user minimized).

*Why a separate gesture from Esc.* Cancel and minimize are different intents — cancel says "stop the work", minimize says "stop showing me the work". Binding them to the same key (with state-dependent meaning) is the kind of overload that gets users to lose data once and never trust the dialog again. Lowercase `m` is unbound on the dialog (the app-level `m`-for-Move binding is blocked while a modal owns the keymap) and mnemonic.

*Resume on an idle queue* — `Ctrl+P` pressed when no plan is running — flashes "No operation in progress" through `StatusLine.flash`, the same idiom `Ctrl+G` already uses when the find-tree cache is empty. No modal, no exception.

*Auto-restore on completion is deliberately off.* `_on_plan_complete` already fires `notify()`, which surfaces a toast even if focus has moved to another app. Auto-popping the dialog after the user explicitly minimized would be jarring (especially if they minimized *because* they wanted to keep working in the panes), and would mean the dialog gets the last word on screen layout against the user's express choice.

*Status-line affordance.* While the queue is running **and** no `ProgressScreen` is on the stack, `StatusLine._build_text` appends `  [Ctrl+P]` to the existing `Copy 3/12 items` readout — discoverable without being noisy. When the dialog is up, the suffix disappears (no point hinting at a key the user can't usefully press from inside the modal). The check is a one-liner against `app.screen_stack` and re-runs every time `_refresh_status` fires (per-item progress, plan start, plan complete) so it tracks dialog state without a new event.

*Mid-plan cancel from a minimized state* requires re-opening the dialog first (`Ctrl+P`, then `Esc`). One extra keystroke for a rare gesture; the alternative (a global `Ctrl+.`-style cancel) risks colliding with editor and pager bindings and is exactly the kind of footgun the minimize/cancel split was meant to avoid.

*Surface wiring.* New `Commands` menu item "Progress dialog" (accelerator `p`); new row in HelpScreen's Application section: `Ctrl+P  —  Show progress dialog (minimized op)`; new row on the dialog hint label so `m = Minimize` sits next to `Esc = Cancel`.

**Wire.** Today's `on_item_progress(item_result, queue)` keeps firing once per item (drives the Files readout). A new `on_bytes_progress(item, bytes_done_in_item, item_size, queue)` fires from inside a chunked `shutil.copyfileobj` for Percent / Data / Rate / Drag. Total bytes-to-transfer is computed at plan time off the already-enumerated tagged set. The dialog and the StatusLine both subscribe; the StatusLine continues to repaint when no dialog is up.

**Tunables.** Two module-level constants in `wtree/ops/queue.py`:

```python
# Bytes per read/write chunk during copy. Tuning notes:
#   - 4 KB   : physical sector on most drives
#   - 64 KB  : Python's shutil default
#   - 256 KB : SSD sweet spot, sensible default here
#   - 1 MB+  : NTFS large-volume clusters, SMB/NFS shares
#   - 4 MB+  : 10GbE → fast NVMe sequential bulk transfers
COPY_CHUNK_SIZE = 256 * 1024

# Maximum progress repaints per second (coalesces per-chunk callbacks).
PROGRESS_REDRAW_HZ = 10
```

Surfaced as constants because anyone running WTree against a specific rig (RAID array, network share, FAT32 thumb drive) will want to align the chunk size to their cluster / sector geometry, and grepping for a single name is friendlier than chasing a magic literal. An `WTREE_COPY_CHUNK` environment-variable override is deferred until someone asks for it.

**Concurrency assumptions.** v0 progress callbacks fire **single-threaded from the asyncio event loop**. `apply_plan` is an `async` coroutine; Textual's loop owns one OS thread; `on_item_progress` and `on_bytes_progress` are invoked from inside that coroutine, so concurrent invocations are impossible by construction. Re-entrancy on the cumulative `bytes_done` counter or the redraw-throttle timestamp cannot happen in v0.

`COPY_CHUNK_SIZE` and `PROGRESS_REDRAW_HZ` are module-level immutable ints — safe to read from any number of threads on any CPython build (GIL or no-GIL), because nobody writes them after import.

The rake — and this is the note for whoever later decides to parallelize per-item copy via `concurrent.futures.ThreadPoolExecutor` (or `ProcessPoolExecutor`) to saturate a fast RAID or NVMe array: doing so makes `on_bytes_progress` fire from worker threads, and the shared mutable progress state then needs explicit synchronization. Specifically:

- **Cumulative counters** (`bytes_done`, `items_done`) — `+=` is `LOAD`/`ADD`/`STORE` at bytecode level, not atomic; under the GIL the window is small but real, under no-GIL builds (PEP 703, Python 3.13+ `--disable-gil`) it's wide open. Wrap mutations in a `threading.Lock`, or use `itertools.count()` for monotonic increments, or — preferred — funnel raw `(item, chunk_size)` tuples through an `asyncio.Queue` via `loop.call_soon_threadsafe()` so all mutation happens back on the event loop thread.
- **Redraw-throttle state** (last-paint timestamp) — must stay event-loop-affine. Worker threads should never call into the dialog's repaint path directly; the queue-funnel approach handles this for free.
- **The constants themselves** — still safe; no change needed.

Until that parallelization lands, none of the above matters. The footnote exists so the trap is documented at the design layer rather than discovered the hard way by the first contributor who reaches for `ThreadPoolExecutor`.

#### Move executor chunk hook

The original progress dialog landed with a known gap: cross-filesystem moves rendered `Rate` / `Drag` as em-dashes because `shutil.move`'s cross-fs fallback uses `shutil.copy2` internally with no chunk-level hook. The fix unwinds `shutil.move` into our own dispatch so the existing `_chunked_copy` path can do the work and the byte-progress callback fires per chunk.

*Same-filesystem moves are unchanged.* The dispatch always tries `os.rename(src, dst)` first — atomic, instant for files / dirs / symlinks of any size, no bytes move. The progress dialog's zero-guard already renders em-dashes for `Rate` / `Drag` when no bytes have flowed, which is the right reading: zero bytes, zero rate. Fast rename-moves often complete before the threshold timer fires and the dialog never shows at all.

*Cross-filesystem moves dispatch by kind.* `os.rename` raises `OSError` on cross-fs (POSIX `EXDEV`, Windows `ERROR_NOT_SAME_DEVICE`); we catch the generic `OSError` rather than inspecting `errno` so the same code works on both platforms (matches `shutil.move`'s own pattern).

- **FILE**: `_chunked_copy(item, src, dst, bytes_progress)` — same path the copy executor uses. On success, `os.unlink(src)` removes the source. Cancel mid-copy: the chunk callback returns `False`, the partial dst is cleaned, source intact, item returns `FAILED("cancelled")`. Partial failure (copy succeeds, unlink fails) leaves the file in both places and surfaces a "unlink source after copy" failure message — same semantics as `shutil.move` today, just with a clearer error.
- **SYMLINK**: read target, recreate at dst, unlink src. No bytes to report. Three short syscalls; no cancel point.
- **DIR**: keep `shutil.move`. Cross-fs dir moves do `copytree + rmtree` internally with no per-file hook; building a recursive walker that chunks each contained file is real code (mid-walk cancel, mid-dir error semantics) and the case is rare enough in daily use that it didn't earn the budget this pass. `Rate` / `Drag` still em-dash during cross-fs dir-move copytree; tracked as a follow-up.
- **OTHER**: skip (matches the copy executor).

*Test-contract fast path preserved.* When `bytes_progress is None` (the test suite's headless case), the FILE branch still falls through to `shutil.move` rather than instantiating a no-op chunk loop. Same pattern `_native_copy` uses: callback present → chunked path; callback absent → fast path. Existing move-executor tests are untouched.

*No new module surface.* `_chunked_copy` is reused as-is; only `_native_move` grows the optional `bytes_progress` arg and the `apply_plan` → `_apply_item` → `_native_move` chain threads it through (mirroring how `_native_copy` does it).

### Scan dialog

For directory scans that exceed a duration threshold — re-rooting at a 100 k-entry folder, expanding a huge tree node, refreshing a deep source — a centered `ModalScreen` reports that WTree is "subcontracting" the scan to an OS call, with a live entry count and Esc-to-cancel. Below the threshold no dialog appears; the pane just repaints.

**Why this is its own surface (not progress-dialog territory).** The progress dialog covers Copy / Move / Delete byte progress. The scan dialog covers `EntrySource.scan(path)` enumeration — a different layer of work with no byte semantics, no `apply_plan`, no per-item progress callback. They share an idiom (centered modal + delayed-show + Esc-cancel) but no code path.

**Delayed-show threshold.** Push the dialog only if the scan is still running after `SCAN_MODAL_DELAY_SECONDS = 0.25` (tighter than the progress dialog's 0.4 s — a paused directory-entry is more disorienting than a paused copy because the user expects copies to take time and directory entries to be snappy). Fast scans never see a flash.

**Chunked consume — load-bearing.** `NativeSource.scan` is an `async` generator that yields synchronously between `os.scandir`'s `readdir` calls. Consumers (`ContentsPane.show_path`, `TreePane._populate`) drained the iterator in a tight `async for` loop with no `await asyncio.sleep(0)` between entries. Result: the event loop ticked, but Textual got no paint frames — the screen froze for the duration of the scan. Without chunking, any dialog we pushed would only become visible *after* the work it was meant to cover had completed. So consumer chunking and dialog ship as one change: every `SCAN_CHUNK_SIZE = 500` entries the consumer yields with `await asyncio.sleep(0)`, giving Textual a frame to paint the dialog and process input.

**Atomic commit on the consumer side.** `ContentsPane.show_path` no longer calls `self.clear()` before iterating — it builds the entries list in a local first, then clears + renders only on successful completion. If the user presses Esc mid-scan the pane keeps its previous listing. (Pre-clearing followed by half-rendering would have left the user looking at an empty pane.)

**`ScanContext`.** A small mutable record shared between the consumer (writes `entries_seen`, polls `cancelled.is_set()`) and the dialog (reads `entries_seen` on a `set_interval` redraw tick, sets `cancelled` on Esc). Fields: `path: str`, `method_label: str`, `entries_seen: int`, `cancelled: asyncio.Event`, `completed: asyncio.Event`. The dialog polls at the same `PROGRESS_REDRAW_HZ` cadence used by the progress dialog; no per-entry subscription (avoids the worker-thread re-entrancy trap noted in the progress dialog's concurrency footnote).

**`scan_method_label` per `EntrySource`.** Each source declares what it subcontracts to. `NativeSource` → `"os.scandir"`. `MockSource` → `"mock source"`. Future `ArchiveSource` → `"zipfile"`, future `SFTPSource` → `"paramiko SFTP listdir"`. The UI renders the label without knowing what it means — the source self-documents the syscall layer. Honest at the Python-API level, not the syscall level (`os.scandir` is `opendir`/`readdir` on POSIX, `FindFirstFileW`/`FindNextFileW` on Windows; the Python name is the one our code actually calls).

**Layout.**

```
┌─ Scanning ─────────────────────────┐
│                                     │
│  /huge/folder/of/100k/things       │
│  via os.scandir                    │
│                                     │
│  12,847 entries...                  │
│                                     │
│  Esc = Cancel                       │
└─────────────────────────────────────┘
```

**Cancellation.** `Esc` sets `ctx.cancelled`; the consumer checks it once per chunk and returns without committing. The dialog dismisses. The pane keeps its previous listing — the cancelled scan is exactly equivalent to "user never pressed L / Ctrl+R / Right / Enter". `Q` and the queue-completion path are not relevant here (there's no queue).

**Application surfaces.** Every "scan a directory" call wraps its work in `await self._run_scan_with_dialog(path, source, do_work)`:

* `L` log new source — re-roots; scan happens on the new root's children.
* `Ctrl+R` refresh source — re-runs `show_path` on the contents pane and `refresh_all` on the tree.
* Cursor onto a big directory in the tree (the `NodeHighlighted` → `show_path` chain).
* Tree-pane Right-arrow expand of a node with many children.
* `Ctrl+F` find-across-tree — already `@work`'d, but a full-tree walk on a deep volume is the case.
* **Recursive tag/untag (Space on a tree node)** — the `_walk_subtree` walk under `on_tree_pane_tag_requested`. Added 2026-06-03: previously this walk had *no* feedback surface (it `@work`'d so the app didn't hard-freeze, but it accumulated the whole subtree and flashed a single count at the end — no in-flight count, no cancel) **and** wasn't chunked, so even a pushed dialog couldn't paint mid-walk. Now wrapped in the gate with the same `await asyncio.sleep(0)` every `SCAN_CHUNK_SIZE` entries; `ctx.entries_seen` drives the live count; **Esc leaves the tagged set unchanged** (the mutation is applied only after the walk completes un-cancelled — atomic-commit, mirroring the pane's atomic-commit on scan cancel).
* **Copy / Move plan-building** — the `plan_copy` / `plan_move` walk + conflict-annotate under `_plan_modal_enqueue`. Added 2026-06-05 after a real freeze: copying a recursively-tagged tree (≈350k tags) wedged the UI with no dialog and no Esc, because plan-building ran to completion off the event loop. The planners now take optional `on_progress` / `should_cancel` callbacks (UI-agnostic plain callables — the ops layer must not import `widgets`, so it does *not* take a `ScanContext`); they `await asyncio.sleep(0)` every `PLAN_CHUNK_SIZE` (a sibling constant to `SCAN_CHUNK_SIZE`, defined in `ops/base.py` to keep the layering clean) and raise `ScanCancelled` when `should_cancel` fires at a chunk boundary. `_plan_modal_enqueue` wires `on_progress`→`ctx.entries_seen` and `should_cancel`→`ctx.cancelled.is_set` into the gate (header `"Planning copy"` / `"Planning move"`) and catches `ScanCancelled` to flash "cancelled" — atomic, nothing enqueued. `_run_scan_with_dialog` was made generic so it returns whatever `do_work` returns (here, the built `Plan`).

**Planner is O(n), not O(n²).** The same change fixed a latent quadratic: `plan_copy` used to call `_entries_for_tag(walk.entries, tag)` once per tag, each a full linear scan of the flat walk — O(tags × entries), which at 350k tags was the dominant freeze cost. `walk_tags` now records `WalkSummary.entries_by_tag` (one sublist per tag, index-parallel, populated as it walks) and `plan_copy` zips `tags` against it directly. `_entries_for_tag` is gone. Semantics are unchanged for the normal (non-overlapping-tag) case; for overlapping tags the grouping is cleaner (each tag owns exactly the entries its own walk produced, no cross-prefix contamination). **Not** addressed (declined this pass): collapsing redundant tagged descendants — recursively tagging a tree still emits one item per already-included descendant; that's a separate semantics call parked for later.

**Configurable header.** `ScanContext` gained a `header: str = "Scanning"` field that `ScanScreen._header_text` renders, and `_run_scan_with_dialog(path, source, do_work, *, header="Scanning")` threads it through. Navigation scans keep "Scanning"; the recursive-tag walk passes "Tagging" / "Untagging" so the modal names the actual operation. The body line still reads `via <scan_method_label>` ("os.scandir") since the underlying enumeration is the same.

A future unified `BackgroundOperationScreen[T]` could collapse `ScanScreen`, `ProgressScreen`, and the in-modal `Computing recursive total...` placeholder in `PropertiesScreen` into one shape; not in scope for the scan-dialog landing but flagged here so the next refactor pass doesn't have to rediscover the symmetry.

### Conflict resolution dialog

Before this landed, conflict handling was split three inconsistent ways across the executor: Move and Rename pre-checked `os.path.lexists(dst)` and **hard-failed** the item; Copy **silently clobbered** files (`shutil.copy2`) and **merged** directories (`makedirs(exist_ok=True)`); Make-new used exclusive-create. The user found out only after the fact, in the result summary. Conflict detection moves that decision to **plan time**, where the user can see it and choose.

**Detection is per-leaf, in the planner.** Each of `plan_copy` / `plan_move` / `plan_rename` stats every `PlanItem`'s `dst_path` (via `dst_source.entry_at(dst_path)`, errors-as-data) and records the result on the item as `conflict: ConflictKind`. `ConflictKind` describes *what already occupies the destination*: `NONE` (free), `FILE`, `DIR`, `OTHER` (symlink / socket / etc.). Detection is the only new async work in the plan phase; it adds one stat per item — O(N) for Copy's flattened leaves, O(tags) for Move, O(1) for Rename.

**The benign-merge rule keeps per-leaf tractable.** For `OperationKind.COPY`, a **DIR** item whose destination already exists **as a DIR** is *not* flagged — directory merge is the existing, correct copy behaviour and surfacing it would bury the real conflicts in noise. Only Copy's leaf **FILE / OTHER** collisions and **type-mismatch** collisions (copying a directory onto an existing file, or a file onto an existing directory) are blocking. Consequence: every blocking Copy conflict sits on a **leaf with no plan descendants** — *except* the rare type-mismatch on a directory node, which still has descendants and so cascades by path-prefix (handled below). For `MOVE` and `RENAME` there is exactly one top-level `PlanItem` per tag, so *any* existing destination is blocking and the cascade is moot.

**`PlanItem` grows two fields**, both defaulted so the dataclass stays back-compatible and the undo-log wire format is unaffected: `conflict: ConflictKind = ConflictKind.NONE` (set by the planner) and `resolution: Resolution = Resolution.PROCEED` (set by the resolution transform; read by the executor). `Resolution` ∈ `PROCEED` (no conflict, or conflict cleared by rename), `SKIP`, `OVERWRITE`, `RENAME`. `SKIP` items are dropped from the plan entirely, so the executor never sees one; `RENAME` rewrites the path and resets to `PROCEED`; only `OVERWRITE` is carried into the executor as a live signal.

**`ConflictDialog(ModalScreen[list[Resolution] | None])`.** Given the list of blocking items, it renders one row per conflict: `<resolution>  <dst_path>  (existing: file/dir)`. Per-row default is **Skip** — the safe, non-destructive choice, so a user who just mashes Enter loses nothing. Keys: Up/Down move the row cursor; lowercase `s` / `o` / `r` set the *current* row to Skip / Overwrite / Rename; uppercase `S` / `O` / `R` set **all** rows at once (the common case — "overwrite everything"); Enter commits the current selections; Esc cancels the **entire operation** (distinct from skipping all — Esc means "I didn't mean to do this at all"). Returns the parallel `list[Resolution]` on commit, `None` on Esc. Reuses the centered-modal idiom but not `ConfirmDialog` (which is a pure yes/no gate); the per-row state needs its own widget. Long conflict lists scroll (`VerticalScroll`), mirroring `ViewerScreen` / `PropertiesScreen`.

**The resolution transform** — `resolve_conflicts(plan, resolutions) -> Plan`, async, pure-ish (stats the filesystem only for collision-free rename names) — rebuilds the plan from the user's choices:

* **Skip**: drop the item. If it's a directory, also drop every item whose `dst_path` is under it (prefix match) — you cannot copy into a directory you declined to create.
* **Overwrite**: keep the item, set `resolution = OVERWRITE`. The executor replaces (see below). Semantics are **replace, not merge**: an explicit Overwrite on a directory means "remove what's there, put mine in its place" — merge is what the *unflagged* dir-on-dir case already does.
* **Rename**: compute a collision-free destination by appending ` (n)` — extension-aware for files (`report.txt` → `report (1).txt`, `foo.tar.gz` → `foo.tar (1).gz` following the same last-`.X` rule as the Rename smart cursor; `proj` → `proj (1)` for dirs), incrementing `n` until `entry_at` reports the name free. Rewrite the item's `dst_path`; if it's a directory, rewrite the prefix on all descendant items too so the subtree follows the renamed root. Clear `conflict` and leave `resolution = PROCEED` — post-rename there is nothing left to resolve.

**Executor honours `OVERWRITE`.** The `lexists` guards in `_native_move` and `_native_rename` stay as TOCTOU race-nets but now fail *only* when the destination exists **and** `resolution is not OVERWRITE`. When `resolution is OVERWRITE`, the adapter pre-removes the existing destination first — `os.unlink` for a file/symlink, `shutil.rmtree` for a directory — then runs the normal `os.rename` / `shutil.move`. Copy's FILE overwrite needs no change (`shutil.copy2` and `_chunked_copy`'s `"wb"` open already clobber); Copy's type-mismatch dir overwrite pre-removes the blocking file before `makedirs`. Delete is unaffected (no destination). **Make-new folds into this flow too** (2026-06-04): a leaf collision is annotated like any other destination collision and routed through the same dialog; `OVERWRITE` calls `_remove_existing_blocking(dst)` (no `src` — see below) to clear the existing entry, then exclusive-creates the empty leaf. The user chose **full Skip/Overwrite/Rename** for Make-new (not a softer Skip/Rename-only) so it stays consistent with Copy/Move.

**App wiring.** `_plan_modal_enqueue` (Copy / Move) and `action_rename` gain a post-plan step: collect `[i for i in plan.items if i.conflict is not ConflictKind.NONE]`; if empty, finalise as before; otherwise push `ConflictDialog`, and on commit run `resolve_conflicts` then finalise. Esc → flash "cancelled". If the transformed plan is empty (every conflict skipped) → flash "nothing to do (all conflicts skipped)" rather than enqueuing a no-op.

**Same-location (self-target) handling.** A special case sits *upstream* of detection: when the user aims an entry at the directory it already lives in, the planner builds `dst_path == src_path`. Statting that destination finds the entry's *own source*, not a real collision — and offering Overwrite there would let the executor `rmtree` the very thing being moved (data loss). A `resolve_self_targets(plan)` pass runs in `plan_copy` / `plan_move` **before** `annotate_conflicts` (which now skips any `_same_location` item, leaving it `NONE`). Per operation: **Copy** is duplicate-in-place — the *topmost* self-targeted item is flagged `ConflictKind.SELF` (a fifth kind) so it surfaces in the dialog defaulting to **Rename** (`name` → `name (1)`, cascading the new prefix onto descendants); descendants stay `NONE` and follow the root's rename-or-skip. **Move / Rename** are genuine no-ops — the item is *dropped* (never offered Overwrite); if that empties the plan the app flashes "already there — nothing to move". Rename's identical-name case was already caught earlier as `NoChange`, so only Copy and Move feed this pass. The user design calls were: Move no-op → **drop + status nudge** (not silent, not a red error); Copy → **confirm via the dialog** (not a silent auto-suffix). Defence in depth: the executor's OVERWRITE pre-step (`_remove_existing_blocking(dst, src)`) refuses — raises, surfacing a `FAILED` item — when the destination *is* or *contains* the source, so a future planner bug or post-plan race can't self-destruct. Inline **editing** of the Rename target landed 2026-06-04: `e` on a row pops a `PromptDialog` pre-filled with the auto `name (1)`; the typed value (a relative subpath is allowed) is validated by `resolve_relative_leaf` and re-stat'd via an async checker, re-prompting on a collision so the chosen name is guaranteed free; the row then shows `-> custom (edited)`. The dialog now dismisses with `(resolutions, custom_dsts)` and `resolve_conflicts` uses a non-`None` custom dst verbatim (cascading onto descendants) instead of the auto suffix. (The live **preview** of the auto-suffix landed earlier the same day; Make-new folding too — see the decision log.)

### Destination browser (Copy / Move)

**Decided + built 2026-06-04** (`wtree/widgets/dir_picker.py`). Copy and Move ask for the destination through a typed `PromptDialog`. The browser adds a navigable picker as a *second* way to choose that destination. It changes nothing downstream: it only supplies the destination path, so same-location detection, conflict resolution, the rename preview, the inline-edit, path normalisation, and the executor all stay exactly as they are — the whole point is that everything after "what is the destination?" is already destination-agnostic.

**Invocation — type-first, `b` to browse.** The Copy/Move destination prompt stays the default (typing a known path is fastest). It gains a browse affordance: pressing **Ctrl+B** (refined from the design's `b` — a plain `b` would be swallowed by the focused `Input`; Ctrl+B is not an `Input` binding) dismisses the prompt with a distinct **BROWSE sentinel** (`PromptDialog.BROWSE`, enabled by a `browse=True` flag); the app pushes the browser; the directory the user picks is fed *back into the prompt* as its pre-filled value. So there is a single confirmation point — Enter in the prompt — and the picked path is still editable before it commits. Esc in the browser returns to the prompt unchanged. The affordance is scoped to the Copy/Move destination prompt only (a `browse=True` flag on `PromptDialog`); every other `PromptDialog` caller (Rename, glob `+`/`-`, `L` log-source, the conflict-editor) is unaffected and `b` stays a literal character there.

**Rooting — top of the current drive / share, cursor revealed at the current dir.** The browser roots at the *anchor* of the current location — `/` on POSIX, `C:\` (or `\\server\share`) on Windows, via `os.path.splitdrive` / `pathlib.PurePath.anchor`. The cursor is then revealed (`reveal_path`) at the current pane directory, so the user starts *where they are* but can climb up to siblings and parents and descend anywhere within that drive. This realises Matthew's "start them at the drive / network level they're on." **Drive / share switching** landed 2026-06-07 (decided below); the first cut covered the whole current drive, which is the overwhelming majority of real destinations.

**Dir-only tree, dedicated lightweight modal.** The picker shows directories only — you copy/move *into* a directory — which is exactly what `TreePane._populate` already does (files live in the contents pane). It is a dedicated `DirPickerScreen(ModalScreen[str | None])` wrapping its own `Tree[str]`, **not** a reused `TreePane`, to stay clear of `TreePane`'s tagging gestures, tagged-set styling, and "authoritative app cursor" coupling. It lifts the proven patterns from `TreePane`: lazy per-directory populate (already dir-only), the line-indexer race fix (`await asyncio.sleep(0)` before reading a freshly-added child's `.line`), `reveal_path` to walk+expand a chain, and Left/Right/Backspace navigation. The scan-*dialog* gate for slow directories is wired into **interactive expands** (2026-06-04): an expand routes through `WTreeApp._run_scan_with_dialog`, so a directory still scanning after the short delay shows a cancellable `ScanScreen`; Esc sets `ctx.cancelled`, the chunked `_populate` polls it between `SCAN_CHUNK_SIZE` entries and returns *before* adding children (atomic — the node stays empty + re-expandable). Fast expands never flash it. The programmatic `reveal_path` walk and the initial root populate stay bare (the cancel-UI is for interactive expands). Enter selects via Textual `Tree`'s `NodeSelected`; `n` is a `@work` worker (push_screen_wait off the message pump). The dir-populate loop is the shared `scan_screen.populate_dir_node(node, source, loaded, *, ctx=None)` (extracted 2026-06-04): both `TreePane._populate` and the picker's `_PickerTree._populate` are one-line delegations to it, so they can't drift.

**Controls.** Up/Down move the cursor; Right / Enter-on-collapsed expands (lazy-populate); Left collapses / moves to parent (as `TreePane`); **Enter chooses the highlighted directory** and dismisses with its path; **Esc cancels** the browse (back to the prompt, unchanged). A title / footer line shows the directory currently under the cursor as the prospective target, and — nice-to-have — the count of tagged items about to land there.

**Make-new-folder — `n` creates and selects.** Pressing `n` prompts for a name, validated by the shared `resolve_relative_leaf` (relative subpath allowed; rejects absolute / `..` / empty — the same helper the conflict-editor uses), re-stat'd for collision (**verify-free**, re-prompt on clash), then created under the cursor directory (lenient intermediate dirs, via the executor's make-new blocking helper — a *direct* create, not an enqueued op, because it is destination setup, not a tagged-set operation). The new directory is then populated, revealed, and selected so the user can immediately pick it. This reuses `resolve_relative_leaf` and the verify-free idiom rather than dragging the full `ConflictDialog` into the picker.

**Drive / share switching (decided + built 2026-06-07).** **Ctrl+D** on the picker pushes a small **`DriveChooserScreen`** modal listing the available drive / location anchors; Enter re-roots the picker tree at the chosen anchor, Esc returns unchanged. A chooser modal was picked over a drives *pseudo-root* (a synthetic top level would special-case `reveal_path` / anchor logic throughout the tree) and over XTree-style bare drive-letter keys (plain letters are reserved for the parked type-to-filter, and letters have no POSIX analogue). Enumeration lives in **`wtree/_drives.py`** (a platform shim, sibling of `_owner.py`): on **Windows**, `os.listdrives()` when available (Python 3.12+), else a `ctypes` `GetLogicalDrives()` bitmask, else an `X:\` exists-probe — no `pywin32`, per the owner-lookup precedent; on **POSIX / macOS**, `/`, `~` (expanded), plus existing one-level children of the removable-media bases `/mnt`, `/media/$USER`, `/run/media/$USER`, `/Volumes` — the pragmatic file-manager convention; full mount-table parsing was rejected as noisy (snap loops, tmpfs) and distro-dependent. The picker's *current root* is always included in the list even when enumeration wouldn't find it (covers a UNC share you're already on; share *discovery* stays parked under Network discovery). **Per-location cursor memory, session-lifetime:** the picker keeps a dict keyed by *root path* (not `splitdrive` anchor — on POSIX every path's splitdrive anchor is `/`, which would collapse `~` and `/mnt/usb` into one key); switching away records the cursor, switching back `reveal_path`s it; first visit lands at the location root; the memory dies with the modal. Scoped to the **picker only** this pass — an app-level Ctrl+D re-rooting the logged tree (a browsable cousin of `L`) is a noted follow-up, and the enumeration helper + chooser are deliberately picker-independent so that wiring stays cheap.

**Out of scope for the first cut (phase 2):** ~~drive / share switching~~ (landed 2026-06-07); type-to-filter / incremental jump inside the browser (will reuse the `/`-search machinery); showing files greyed-out for context (dir-only is the rule).

## Error handling and crash reporting

**Decided 2026-06-05: a vendored `describe_error` crash reporter wired into the one delivery point Textual actually uses.** WTree had no crash handler of its own — an unhandled exception in the event loop surfaced as Textual's built-in Rich traceback dump. This section is the durable design for the reporter dropped in from the sibling `Python ErrorHandler` project.

**The Textual constraint that shapes the whole design.** Textual's `App.run()` (via `run_async`) does **not** re-raise unhandled exceptions in normal operation. When a handler / timer / worker raises, Textual's `App._handle_exception` stashes the exception, renders its own Rich traceback to the exit screen, sets the return code to 1, and `run()` returns *normally*. (The `raise self._exception` path exists only under the test pilot.) Consequence: a `try/except` around `main()` cannot see in-loop crashes — the exact class of bug we care about (e.g. the 2026-06-05 `ScanScreen` double-dismiss). The only reliable interception point is `_handle_exception` itself.

**Mechanism (two nets).**

1. **`WTreeApp._handle_exception(self, error)` override — the primary net.** Builds `report = describe_error(error)`, writes the full report to a crash logfile *immediately* (so a subsequent hard kill during teardown can't lose it), stashes `self._crash_report` on the instance, then calls `super()._handle_exception(error)` so Textual's own teardown + Rich dump proceed unchanged. We deliberately **keep Textual's dump** (decision: simplest, robust) and merely add our logfile alongside it; fully owning the exit screen with a clean one-panel message is a parked phase-2 option.
2. **`main()` `try/except` — the secondary net.** Catches exceptions *outside* the loop (app construction, import-time, teardown) which `_handle_exception` never sees, routing them through `describe_error` too. After `run()` returns, if `self._crash_report` is set (in-loop crash), `main()` prints a one-line pointer — `WTree hit an error — full report written to <path>` — to stderr and exits non-zero. The Rich dump the user already saw on screen is left as-is.

**Crash log location.** `~/.wtree/crashes/crash-<UTC-ISO>-<pid>.log`, created lazily. Each file holds the `for_claude()` flavor (labelled, LLM-friendly — these get pasted into a Claude chat for diagnosis) followed by the `to_dict()` JSON for any structured post-processing. **Never written inside the project folder** — that mount is flaky (see the mount-rules memory) and a crash mid-write there is the worst time to trust it; `~/.wtree` is on the user's real home filesystem.

**Locals capture.** `include_locals=False` by default, because frame locals can hold secrets. Setting `WTREE_DEBUG=1` in the environment flips `include_locals=True` for richer post-mortems — opt-in only, name fixed as `WTREE_DEBUG`.

**Default redactors.** Because crash logs persist to disk, WTree registers a small default scrub set at startup (API-key shapes like `sk-…`, `password=…`, `token=…`) via the reporter's `register_redactor` / `redact_pattern` hooks, so a secret that happens to sit in a source line, arg, or (with `WTREE_DEBUG`) a local is masked before it lands in the log.

**Vendoring.** `error_handler.py` is copied verbatim into `wtree/error_handler.py` (single file, pure standard library, zero new dependencies) with a provenance header recording the sibling-project git rev it was synced from. It is treated as vendored third-party code — bug fixes flow upstream in `Python ErrorHandler` and are re-synced, not forked in place. The thin WTree-specific glue (log path, default redactors, `WTREE_DEBUG` gate, the pointer message) lives in `wtree/crash.py`, keeping `app.py` lean and the vendored file untouched.

## Language and toolkit

**Decided: Python with [Textual](https://textual.textualize.io/).**

Target platforms: **Windows, Linux, macOS** — all three.

Why this works:

- **Async-native.** Textual's event loop is `asyncio`. `EntrySource.scan(path)` is an `async` generator; long scans yield to the UI naturally without threading.
- **Cross-platform.** Textual renders cleanly on Windows Terminal, WezTerm, iTerm2, and modern Linux terminals. Legacy `cmd.exe` / old conhost work but look rougher — Windows users will be pointed at Windows Terminal in the README.
- **Standard-library leverage.** `pathlib`, `shutil`, `subprocess`, `asyncio.create_subprocess_exec` cover most needs. ShellSource is a near-trivial wrapper.

**Distribution strategy** — decided later. Candidates: `pip install wtree` for users with Python; PyInstaller or Nuitka for standalone binaries. Not a v0 blocker.

**Considered and rejected** — Rust (ratatui), Go (bubbletea), C (ncurses). All viable; Python wins on dev velocity for this project's scope and on author preference.

## Parking lot — post-v0

- **Inline editor.** Big scope. MC ships mcedit; vifm wisely shells out. Revisit only if shelling out to `$EDITOR` proves friction-laden in practice.
- **Archive browsing.** `ArchiveSource` — `.zip`, `.tar`, `.tar.gz` as virtual directories.
- **Remote sources.** SSH/SFTP, possibly WebDAV.
- **Network discovery.** SMB / Bonjour / mDNS browsing — enumerate available servers and shares rather than requiring the user to type `\\server\share` from memory.
- **Live filesystem watching.** `inotify` / `FSEvents` / `ReadDirectoryChangesW` for auto-refresh.
- **Bookmarks and history.** Persistent named locations, MRU directory list, jump-to-recent.
- **Batch rename.** Pattern-based rename across the tagged set.
- **Themes.** Color schemes, including a faithful XTree green-on-black.
- **Mouse support.** Decision pre-committed for when this lands: click = navigate only (move cursor / select row / expand-collapse tree node); wheel scrolls both panes; F-key bar and MenuBar entries become clickable proxies for their key bindings; tagging stays keyboard-only (Space / T / + / - / Ctrl+A / Ctrl+U); Textual's `ModalScreen` scopes events per screen so existing modals (PromptDialog, MenuScreen, kind-chooser) intercept clicks for free without extra guards. **Drag-to-range-tag and Ctrl/Shift-click-to-tag are rejected on principle, not deferred by default.** The principle: *mouse adds discoverability, not new semantics.* Tagging behaviour must not depend on input device because the tagged set is persistent across directory navigation, source-agnostic (multi-drive, post-v0 multi-source), and decoupled from the cursor — Shift+click range-extend has no clean meaning when the anchor row lives in a different directory or on a different drive than the current view; scoping it to current-view-only creates a confusing two-tier model (Space tags anywhere, Shift+click only tags here). Drag-tag adds a contiguous-only gesture whose keyboard equivalents (`Ctrl+A` for the whole dir, `Space ↓ Space ↓ …` for a run, `+ glob` for a pattern) are already atomic and viewport-independent. Both gestures also import a stack of UX traps — auto-scroll-on-drag, drag-out-of-widget, click-jitter threshold, cross-pane drag boundaries, modifier-state-changes-mid-drag — that bloat scope for zero new capability. The TUI-context framing matters too: a mouse pointer in a text-only GUI is inherently a tacked-on accelerator, not a primary modality, and the design should reflect that. README will note: requires a modern terminal (Windows Terminal, iTerm2, WezTerm, recent Linux terms); tmux users need `set -g mouse on`; hold **Shift** to bypass app mouse reporting and use the terminal's native click-to-select-text for copy.
